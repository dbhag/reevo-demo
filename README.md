# Import Dry Run

Reevo replaces the customer's CRM outright, so every deployment opens with a
bulk load of a legacy system's full history into an empty instance. A naive
importer reports zero errors before it runs because it counts rows, not
outcomes. This is a dry run for that import — the analogue of Reevo's own
Workflow Dry Run, on the surface that doesn't have one.

**Live:** https://dbhag.github.io/reevo-demo/

**Run it:**

```bash
git clone <this repo> && cd reevo-demo
make demo
```

Python 3.12 (3.10+ enforced by the Makefile). One dependency, pinned:
`pip install -r requirements.txt` (PyYAML; everything else is standard
library). `make demo` generates the synthetic dataset, runs the audit, and
renders `dashboard.html` — self-contained, opens directly in a browser.

## The finding

4,000 opportunity records, run through parsing, rule checks, stage
resolution, and gate validation. Three outcomes:

| | count |
|---|---|
| Will import clean | 2,624 |
| Will import **and silently corrupt reporting** | 526 |
| Blocked — would throw an error | 850 |

The middle bucket is the product. Nobody's trust is damaged by the 850 —
the customer sees those immediately. The 526 import without complaint and
break a specific report later:

- inactive, blank, or absent owner → **rep leaderboard and quota attainment**
- null close date on a closed deal → **cycle-time and pipeline velocity**
- stage mis-mapping → **stage-conversion rates and weighted pipeline forecast**
- fuzzy-duplicate deals → **inflated pipeline totals**

The 850 blocked and 526 corrupted don't resolve to a stage cleanly enough to
act on automatically. Grouped by the actual decision needed — not by row —
that's **7 decisions**, not 4,000 rows to review by hand.

**Canonical example:** legacy stage `Verbal Commit` fuzzy-matches
`Negotiation` at **0.87** confidence, against a **0.90** auto-map threshold.
Flagged for a human decision, not mapped. Full candidate list: Negotiation
(0.87), Proposal (0.38), Closed Lost (0.35). Plain character similarity,
with no synonym help, scores Verbal Commit against Negotiation at **0.25** —
and ranks Closed Lost (0.33) above it. The naive approach doesn't just
mis-map this one; it doesn't surface the right answer as a candidate at all.

## Limitations

This section is the point, not a disclaimer.

**Synthetic data.** Every corruption class is sourced to a documented
real-world migration failure (see [DATASET.md](DATASET.md)), but the mess
itself is authored — generated by a script this tool's own confidence
threshold was tuned against. On a real export it will over- and under-flag
differently. Nothing here is calibrated on production data.

**The 526 headline number is inflated, and here's the exact amount.** The
dashboard's silent-corrupt bucket (526) doesn't match the ground-truth
manifest (425 rows tagged SILENT). Decomposed: **+138** rows pulled in by
findings the manifest doesn't tag — almost entirely fuzzy-duplicate false
positives landing on otherwise-clean rows — offset by **−37** rows the
manifest tags SILENT that show as clean, because class A3 (below) is
undetectable by design. Net: 425 + 138 − 37 = 526. The true count of real
defects is closer to 425 than to 526.

**Fuzzy duplicate-deal detection (F3):** 238 rows flagged to find 30 real
duplicates — 30 caught, 208 false alarms. **12.6% precision, 100% recall.**
False positives cluster around same-account pairs with different deal types
(Renewal vs. Expansion for the same company) created about a week apart —
legitimate concurrent business, not a vocabulary artifact.

**Stage resolution's synonym lexicon is hand-curated against a known answer
key, not learned.** It fixes the canonical case (Verbal Commit: 0.25 → 0.87)
and amplifies an existing wrong answer on another (Pilot → Closed Lost:
0.38 → 0.67, still wrong — plain similarity already ranked Closed Lost top
for Pilot before the lexicon touched it). Neither the threshold nor the
lexicon was retuned after finding the Pilot case.

**Class A3 — same stage name, different meaning across teams — is not
detectable from data alone.** In this dataset, `Qualified` maps cleanly to
`Qualification`; the record looks identical to a correct mapping. The tool
catches it here only because the generator knows the answer (37 of the 40
injected instances land in the clean bucket regardless). On real data this
requires asking a human, not running a better algorithm.

**Deterministic checks show 0 false positives and 0 false negatives against
the manifest.** This is agreement-by-construction between the generator and
the checker, not evidence of accuracy on real data — the same engineer built
and calibrated both. Its value during this build was surfacing concrete
defects (cascading false triggers, a signal-destroying `.strip()`,
account/company binding bugs), not the 0/0 score itself.

**Display-only confidence floor at 0.60.** Below it, the decision list and
drill-down show "no meaningful candidate" instead of a stage name. This is a
presentation choice — it does not change resolution logic, the 0.90
threshold, or any verdict.

**Scope.** Opportunities only. Accounts and contacts are deliberately
excluded (see [CLAUDE.md](CLAUDE.md)) — Reevo already claims automatic
validation and dedupe there. Read-only: this tool writes nothing, syncs
nothing, touches no production system.

## What I'd do next, with a real export

Not a feature list — what actually changes once the input is real.

- **Recalibrate the 0.90 threshold against a real export.** The current
  value is defensible only against this dataset's own generator; a real
  legacy pipeline's naming conventions will land differently.
- **Replace the hand-curated synonym lexicon with mappings derived from the
  customer's actual legacy stage vocabulary**, not phrasing one engineer
  anticipated.
- **Name which silent classes require a human decision and build that
  review into the interface** — the decision list already groups by
  distinct legacy value, not by row; it needs an approve/reject action per
  group, not per record.
- **Get a real F1 check.** Account-reference validation is blank/absent-only
  right now because accounts are out of scope; closing that gap needs a
  real account roster, not a bigger heuristic.
- **Define what "pre-go-live" requires operationally**: read access to the
  actual export and target config, sign-off that this stays advisory with no
  write path, and a decision on who owns resolving the human-decision list
  before cutover.

## Recurring failure mode

Three defects in this build had the same shape: something that looked
correct because it was never actually exercised, or agreed with itself by
construction.

`gate_missing_owner`'s "is this already covered?" guard tested the identical
condition that triggered the check, making it unreachable regardless of
input — not undertested, structurally dead. Gate validation as a whole fired
zero times until the dataset was deliberately extended with a class that
exercises it. And the Verbal Commit/Negotiation plain-similarity figure was
hardcoded as 0.31 in this README and the report for a full working session,
disagreeing with the actual computed value (0.25) the whole time, until it
was caught by re-deriving the number instead of trusting the earlier text.

All three were caught by cross-checking against the ground-truth manifest
and by computing values instead of restating them from memory — not by
reading the code and trusting it looked right. A check with 0 findings looks
identical whether it's passing or dead. The dashboard was verified the same
way, against behavior instead of source: a headless DOM run (jsdom) driving
actual clicks caught an unguarded `scrollIntoView` call that would have
silently broken the canonical-example jump button.
